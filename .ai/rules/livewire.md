# Livewire

## No direct DB queries in Livewire components
A Livewire component must never call `Model::query()`, a relation method that issues its own fresh query (`->children()`, `->where(...)`, etc.), or any other direct Eloquent/DB query itself — not even as a fallback for an edge case. All reads belong in an Action, a pipeline stage, or a `Queries/` class (see the Queries rule in `app.md`); a component only ever consumes what one of those already handed back (e.g. via `componentContexts` from a pipeline Action) or something cached on the component from an earlier such call. This applies to every Livewire component, not just `PlayConfigurator` — see that class for the concrete pattern (private, per-request render caches sourced entirely from `FetchConfigurationState`).

## View widgets are config-driven, not type-driven
ViewType is only {Group, Input, Display} — a family/dispatch key, not a control type. Which control an Input renders as (text/checkbox/select/color/date/email/number/radio/range/datalist) lives in config['widget'], an open-ended string, and item.blade.php dispatches to resources/views/livewire/play-configurator/widgets/{widget}.blade.php by naming convention — one partial per widget, never an if/elseif chain. A field's default value is the explicit config['default'] (author-set), not inferred from the widget name. PlayConfigurator/backend code must never branch on a specific widget name (e.g. checking for 'checkbox') — that knowledge was deliberately removed from the backend so it stays widget-agnostic; new widgets should only ever require a new config['widget'] value + a new Blade partial.

## Group multiselect: children keep independent answers
A Group with config['widget']='multiselect' renders one <select multiple> whose <option>s are its children, but each child still gets its own independent scalar Answer — the Group itself never has a directly-attached Answer. updatedGroupSelections() must not trust its own arguments: Livewire's <select multiple> binding can deliver a bare scalar instead of an array, or a granular per-index dotted path (groupSelections.{groupId}.0) that corrupts $groupId with a trailing '.0' (breaks the ->find($groupId) UUID lookup). Always strip anything from the first '.' in $groupId (UUIDs never contain dots) and read the authoritative selection from $this->groupSelections[$groupId] — already correctly hydrated by Livewire before the hook fires — rather than the raw hook argument.

## How PlayConfigurator satisfies the no-queries rule: everything comes through FetchConfigurationState
Every view/answer record `PlayConfigurator` renders comes from `FetchConfigurationState`'s `componentContexts` (already hydrated `View` models — `componentContexts['scope']` is a full tree via `bloodline->toTree()`, `componentContexts['breadcrumbs']` an ordered `Collection<View>`), cached on two **private** (not `public`) properties, `$scopeViews` (flattened, keyed by id) and `$breadcrumbViews`, set inside `fetch()`. Being private means they never survive Livewire's dehydrate/hydrate cycle between requests — that's fine, `fetch()` unconditionally repopulates both from a fresh `FetchConfigurationState` call every time it runs, and every public action method calls `fetch()` before `render()` can read them. Before adding any read to this component, check whether it's already sitting in `componentContexts` rather than reaching for a query — e.g. `$breadcrumbViewIds` (public, survives across requests) already gives `back()` "the previous step" as the array entry before the current one, and `loadGroupSelections()` caches a multiselect group's already-loaded `children` relation into `$groupChildViewIds` for `updatedGroupSelections()` to read on the next live toggle, rather than re-querying.

Two things that are easy to get wrong when touching this:
- `$advanceScope` only gates the **public** `$scopeViewIds` (which must stay pinned across live edits until an explicit commit/navigation — see the pinning rule below); the **private** `$scopeViews` cache is always refreshed from the current `fetch()` call's evaluation regardless of `$advanceScope`, since a private property has nothing to fall back to on a fresh request instance. This is safe only because `ApplyFlow`/`GuardAnchorOverride` compute scope from *persisted* answers/chunks only, never pending ones — a live edit's `componentContexts['scope']` is therefore always identical to whatever was last pinned, so refreshing the cache from it can't leak an unwanted advance.
- `next()`'s validation-failure branch deliberately does not call `fetch()` — doing so would overwrite the strict commit-time validation errors (`ApplyValidation(requireVisible: true, throwOnFailure: true)`) with the weaker fetch-time ones. It still needs `$scopeViews`/`$breadcrumbViews` populated for the render that follows, so it calls `refreshRenderState()` instead — a second `FetchConfigurationState` call that only harvests scope/breadcrumbs and leaves `$fieldErrors` alone.

## goToView()/back() pin scope via $requestedAnchorViewId, not a separate mechanism
Going back to an already-answered step reuses the same `fetch(bool $advanceScope)` machinery that already keeps scope fixed across live edits — there is no separate "navigation mode". `goToView()` sets `$this->requestedAnchorViewId` (also clears `$values`/`groupSelections` so stale fields from the step being left don't leak into the next commit) and calls `fetch(advanceScope: true)`; every subsequent `fetch()` call — including the ones triggered by live edits via `updatedValues()`/`updatedGroupSelections()` — must keep passing `$this->requestedAnchorViewId` through to `FetchConfigurationState`, or a live edit while revisiting a step would silently jump scope back to wherever forward computation naturally leads. `next()` clears `$this->requestedAnchorViewId` right after a successful commit so forward flow resumes normally. Don't add a second, parallel "current view" property for this — it belongs on the one property already threaded everywhere `anchorViewId` matters. `back()` finds the previous chunk via `relevantAnswerChunks()->reorder('sequence', 'desc')` — see the models rule on why a plain `orderByDesc` there silently returns the wrong end of the list.
