# Pipeline

## String templating via {{ }} substitution, not inline expressions
`View.config['label']`/`config['content']`/`config['options'][].label` and `Rule.meta['message']` support `{{ expression }}` substitution, resolved by `ResolveTemplate` (never inline arithmetic — real math stays in the `Calculation` component; a template can only reference `answers[id]`/`calculation.name`/`label(id)`/`message(id)`).

`label(id)`/`message(id)` are ExpressionLanguage functions (registered in `ExpressionLanguageServiceProvider`) backed by the `config/templating.php` `fields` registry (model class → field name → accessor) via `ResolveTemplateField`/`BuildTemplateFieldContext` — extend that registry, not the resolver, when a new item type/field needs to be cross-referenceable.

Which `View.config`/`Rule.meta` keys self-resolve is entirely config-driven, and `ResolveTemplateStrings` itself has zero model-specific logic — all template resolution happens only there, never inline in another pipeline action. `config/templating.php`'s `resolvable` is a flat list of entries (not keyed by `ComponentType` — there's no `componentContexts['validation']` to key against yet, since `ApplyValidation` produces that *after* `ResolveTemplateStrings` runs), each with `context`, `iterate`, `resolve`, and `keys`. For every entry, `ResolveTemplateStrings` reads `$evaluation->componentContexts[$entry['context']]` and calls `iterate($items, $visit)` with exactly that collection and a `$visit` callback — nothing else from `componentContexts` is reachable. `iterate` owns traversal and calls `$visit($item)` for every item to resolve. Both current entries declare `context => ComponentType::Scope->value`, since rule messages live nested under `View->rules` in the same tree, not in their own componentContext: one entry walks views via `$view->children` and visits each view; the other walks the identical tree but visits each view's `rules` instead. `$visit` is wired to that entry's `resolve` closure — `resolve($item, $keys, $resolveTemplate, $context)` — which owns reading/writing the templatable field on that item (`$view->config` for the view entry, `$rule->meta` for the rule entry) and, for each key present in `keys`, calls the resolver closure with that key's current raw value (not the model), the `ResolveTemplate` action, and the context, writing back whatever comes out. Add a new self-resolving key under an existing entry's `keys`, or a whole new list entry (with its own `context`/`iterate`/`resolve`/`keys`) for a different field/model — never in `ResolveTemplateStrings` or in the action that consumes the resolved value (e.g. `ApplyValidation` just reads `$rule->meta['message'] ?? 'invalid'`, with no `ResolveTemplate` dependency of its own).

Any unresolved reference (unknown id, not-yet-answered, or a circular label/message reference) falls back to printing the raw `{{ ... }}` text — never throws. `content` escapes only the substituted *value* (`escapeValues: true`, since it renders via `{!! !!}`); `label`/`options[].label`/`message` must NOT be pre-escaped, since Blade's own `{{ }}` already escapes the whole resolved string at render time and double-escaping would corrupt entities.

`BuildTemplateFieldContext` sits early in `FetchConfigurationState::PREFIX` (right after `GuardAnchorOverride`) so `label()`/`message()` context is available to every later stage. `ResolveTemplateStrings` mutates `componentContexts['scope']` Views (and their loaded `rules`) in memory, never persists, and runs in *both* the fetch and commit pipelines — `CommitConfigurationAnswers` runs it right after `FetchConfigurationState::PREFIX` and before `ApplyValidation`, since a thrown `ValidationFailedException`'s messages are surfaced straight from that pipeline's own evaluation (`PlayConfigurator::next()`), not from a later re-fetch.
