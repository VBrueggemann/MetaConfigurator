# Rules engine

Applies to: `app/**` (rules/pipeline/expression evaluation code)

The two actions that run a pipeline (`FetchConfigurationState`, `CommitConfigurationAnswers`) live at the root of `app/Actions/`. Every pipeline stage and helper they orchestrate (`GuardAnchorOverride`, `ApplyFlow`, `CollectAndBatchFetchExternalReferences`, `ApplyCalculation`, `ApplyVisibility`, `ApplyValidation`, `ApplyBreadcrumbs`, `SupersedeAnswerChunks`, `CommitAnswers`, `EvaluateExpression`, `EvaluateRule`, `ResolveModelFunction`, `ResolveTemplate`, `ResolveTemplateStrings`) lives in `app/Actions/Pipeline/` — an Action never belongs in `Pipeline/` unless something else's pipeline invokes it. `EvaluateExpression` wraps `symfony/expression-language`; `EvaluateRule` evaluates one `Rule` against a context array. New pipeline stages should follow the same convention (see `actions.md`).

- The rules engine is two independent `Illuminate\Pipeline\Pipeline` runs, each threading one shared `ConfigurationEvaluation` object every stage reads and adds to. `context` is now nearly empty — only `calculation` (named formula results, not view-keyed) and the ingredients `CollectAndBatchFetchExternalReferences` populates (`modelsById`, `relevantAnswers`, `relevantAnswerChunks`, `pendingAnswers`) live there. `componentContexts` only ever has two keys: `scope` (the anchor's `bloodline->toTree()`, everything else hangs off it — see `pipeline.md`) and `breadcrumbs` (fully separate, `AnswerChunk`-history based). Both pipelines share a common prefix, which each splices into its own list rather than one wrapping the other:
  - **`FetchConfigurationState`**: `GuardAnchorOverride → ApplyFlow → CollectAndBatchFetchExternalReferences → ApplyCalculation → ApplyVisibility → ResolveTemplateStrings → ApplyValidation(throwOnFailure: false) → ApplyBreadcrumbs`. Read-only preview of user input, never throws, always computes breadcrumbs.
  - **`CommitConfigurationAnswers`**: same prefix through `ResolveTemplateStrings`, then `ApplyValidation(throwOnFailure: true) → SupersedeAnswerChunks → CommitAnswers`. A failure throws `ValidationFailedException`; `CommitConfigurationAnswers` catches it and returns the same (already-mutated) `$evaluation` object — callers (`PlayConfigurator::next()`) read the surviving Validation rules straight off `componentContexts['scope']`, same as the non-throwing path. `SupersedeAnswerChunks`/`CommitAnswers` no longer re-check validation themselves — reaching them at all means it already passed. No breadcrumbs are computed on commit; `PlayConfigurator::next()` already discards the commit pipeline's evaluation on success and re-fetches for rendering, so this was previously wasted work.
  - `ApplyValidation` no longer takes a `requireVisible` flag — `ApplyVisibility` (which now runs before it and prunes invisible nodes out of `componentContexts['scope']` unconditionally) already removed anything invisible from the tree by the time validation runs, so there is nothing left to conditionally validate. This is a real behavior change from the pre-consolidation pipeline: fetch no longer surfaces a validation error for a pending answer on a currently-hidden field, since that field's node is simply gone from the array before validation ever sees it.
  - `ApplyFlow` runs before `CollectAndBatchFetchExternalReferences`/`ApplyCalculation` now (it used to run after `ApplyCalculation`), since the scope tree has to exist before the batch stage knows what's in-scope vs external. One consequence: a Flow rule can no longer reference `calculation.<name>` — nothing currently does, but if a configurator needs that, `ApplyFlow` would need its own local calculation pass, not a shared `context['calculation']`.
  - Do not reintroduce an independent-events design — the stages genuinely depend on each other's output (see `docs/adr/0003-rules-engine-as-dependent-pipeline.md` for the *reasoning*, though its concrete stage list is stale — this rule is the current source of truth for the stage list itself). Do not go back to one pipeline wrapping the other, either — that's what made it impossible for fetch and commit to validate differently in the first place.
  - When a stage needs different behavior per pipeline, pass a container-built instance into `.through()` instead of the bare class-string: `app(ApplyValidation::class, ['throwOnFailure' => true])` — the container still auto-resolves the stage's other dependencies (e.g. `EvaluateRule`), only the differing flag is given explicitly. Don't add a mode enum to `ConfigurationEvaluation` for this — the two pipelines are independent call sites, so config belongs at construction, not threaded through the shared DTO.
- There is no `ResolveCurrentGroup`, `EvaluateGroup`, or stored/pointer-based "current group" — scope is still fully recomputed from persisted state every request via depth-based resolution in `ApplyFlow` (a `Scope` component's `config.depth` says which generation of the view tree is the current page/step; `ApplyFlow` picks the anchor view at that depth and its whole `bloodline` becomes the visible scope). The one deliberate exception: `ConfigurationEvaluation::$anchorViewId` can be pre-set by a caller (`PlayConfigurator::goToView()`/`back()`) to request a specific anchor instead of the computed one — `ApplyFlow` honors it directly, skipping the Flow-rule scan and `lastAnsweredAtDepth` fallback entirely, but only after `GuardAnchorOverride` has verified it names an existing relevant `AnswerChunk` anchor (silently clearing it otherwise). This field stays an explicit scalar on `ConfigurationEvaluation` (both the override input and the resolved output) deliberately — `CommitAnswers`/`SupersedeAnswerChunks` need a reliable value even after `ApplyVisibility` has since pruned/reshaped `componentContexts['scope']`, so it's never derived from the tree. If you find either "ResolveCurrentGroup" or "EvaluateGroup" mentioned elsewhere (older ADRs, comments), treat it as historical, not current.
- **`ApplyFlow`'s Flow-rule scan is bounded to the last-answered step, not the whole tree.** It still needs the whole tree loaded (finding the anchor is inherently whole-tree work, independent of what `componentContexts['scope']` ends up holding), but the reverse/latest-wins scan for a firing Flow rule only considers views from the last-answered step's position onward — a Flow rule positioned earlier than that is never reconsidered. This is safe specifically because revisiting an already-answered step supersedes every later `AnswerChunk` (see the "Answered" bullet below), which rolls the boundary back to the edit point — there's no scenario where an earlier, now-newly-true Flow rule gets silently skipped. When nothing is answered yet, the scan covers the full range (matches the existing lowest-order-at-depth fallback).
- **"Answered" means "covered by a relevant `AnswerChunk`", not "has an `Answer` row".** Answers are append-only (`answers.answer_chunk_id`, no more unique `(configuration_id, view_id)`) — a view can have multiple historical `Answer` rows, only the one(s) whose chunk has `relevant = true` count as current. `ApplyFlow`'s `lastAnsweredAtDepth` and `answer(id)`'s resolution (see `pipeline.md`) both filter to `Configuration::relevantAnswers()`/`relevantAnswerChunks()` — never the raw `answers()`/`answerChunks()` relations, which include superseded history. Revisiting an already-answered step (via the anchor-override above) makes `SupersedeAnswerChunks` mark that chunk and every later one (by `sequence`) `relevant = false` before a fresh chunk is committed; see `docs/adr/0007-back-navigation-via-answer-chunks.md` for the full reasoning, including why this is append-only rather than update-in-place or delete-on-revisit.
- **Groups never get a physical `Answer` row.** A Group view has no field value of its own, so "was this step completed" is derived, not stored: `answer(id)`'s resolve falls back to `true` whenever that view is the `anchor_view_id` of a relevant chunk and nothing else was found in its own-or-descendant answers. This is why `answer('{$step->id}') == true` Flow-rule expressions (see `WidgetShowcaseSeeder`) work with zero rows ever written for the group itself — do not "fix" this by writing a real Answer for a Group id, and do not assume `Configuration::answers()` contains one row per visited step.
- `ComponentType::Breadcrumbs` (`ApplyBreadcrumbs`) lists the views that are anchors of a relevant chunk, in `sequence` order — i.e. the steps actually visited so far, not "views structurally shallower than the configured depth" (that was the pre-chunk implementation, and was wrong for branching flows: a sibling branch never taken is structurally shallower than nothing, but nothing in it was ever answered). This is also the eligible-target set for `PlayConfigurator::goToView()`.
- `RuleComponent` is `{Visibility, Validation, Flow}` — "next-group" was renamed to `Flow`. A Rule's `component` field says which stage owns it; `meta` is a JSON payload the owning component defines (a `Flow` rule's `meta.view_id` names the View to jump to when it fires).
- `ComponentType` is `{Visibility, Validation, Calculation, Scope, AnsweredViews, Breadcrumbs, PendingViews}` — one `Component` row per configurator per type holds pipeline-wide config (e.g. `Scope.config.depth`, `Calculation.config.formulas`). Only `Scope` and `Calculation` are read as `Component` rows by the pipeline now; `Visibility`/`Validation`/`Breadcrumbs`/`PendingViews` are no longer `componentContexts` keys at all (see `pipeline.md` for what replaced each). `AnsweredViews` remains a recognized `ComponentType` for a future component that needs it, not dead code to remove on sight.
- Polarity is uniform: a Rule's expression evaluating `true` means its effect applies. Visibility: `true` → shown (default shown if no rule targets it). Validation: `true` → the answer is *valid*. Flow: `true` → jump to `meta.view_id`.
- For a purely linear multi-step wizard (no branching), give **every** step an explicit `Flow` rule (`answer('previous step id') == true`) rather than relying on `ApplyFlow`'s fallback (`lastAnsweredAtDepth`) to advance automatically — that fallback loops back to the first step whenever the last-answered view is nested deeper than the target scope depth, which is the normal case as soon as any leaf field inside a step has an answer.
- `Rule.expression` strings are evaluated with `symfony/expression-language`, and may contain `&&`/`||` themselves for compound logic. There is no separate Condition model or conjunction column (see `docs/adr/0006-view-unification-and-rule-condition-merge.md`).
- `this` inside a `Rule.expression` always means that rule's own `view_id` (see `pipeline.md`) — e.g. `answer(this) != null` on a field's own Validation rule, instead of spelling out that field's id.
- `ApplyCalculation` reads a `Calculation` component's `config.formulas` (name → expression) — via `context['calculationFormulas']` if `CollectAndBatchFetchExternalReferences` already fetched it this run, else its own query — topologically orders them so a `calculation.<name>` reference resolves regardless of declaration order, and stores results on `$evaluation->context['calculation']`. Formulas, Flow rules, and Visibility rules all operate on raw PHP scalars from `answer(id)`/`context['relevantAnswers']` — no `ViewType`-specific coercion happens anywhere in the pipeline (see the `ViewType` rule for why).
- Auto-select is a recognized Rule component in the domain (see `CONTEXT.md`) but is intentionally unimplemented until a Configurator needs it. If you add it, it slots into the pipeline before validation.
