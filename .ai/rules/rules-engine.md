# Rules engine

Applies to: `app/**` (rules/pipeline/expression evaluation code)

Expression evaluation lives in `app/Actions/Rules/` as invokable Actions (see `actions.md`): `EvaluateExpression` wraps `symfony/expression-language`; `EvaluateRule` evaluates one `Rule` against a context array. Pipeline stages should follow the same convention.

- The rules engine is an `Illuminate\Pipeline\Pipeline` (`FetchConfigurationState`), run in the fixed order **`GuardAnchorOverride → BuildAnswerContext → ApplyCalculation → ApplyFlow → ApplyVisibility → ApplyValidation → ApplyBreadcrumbs`**, threading one shared `ConfigurationEvaluation` object each stage reads and adds to (`context` for freeform data like `answers`/`calculation`, `componentContexts` keyed by `ComponentType`). `CommitConfigurationAnswers` runs that same fetch pipeline and then a second one, **`SupersedeAnswerChunks → CommitAnswers`**. Do not reintroduce an independent-events design — the stages genuinely depend on each other's output (see `docs/adr/0003-rules-engine-as-dependent-pipeline.md` for the *reasoning*, though its concrete stage list is stale — this rule is the current source of truth for the stage list itself).
- There is no `ResolveCurrentGroup`, `EvaluateGroup`, or stored/pointer-based "current group" — scope is still fully recomputed from persisted state every request via depth-based resolution in `ApplyFlow` (a `Scope` component's `config.depth` says which generation of the view tree is the current page/step; `ApplyFlow` picks the anchor view at that depth and its whole `bloodline` becomes the visible scope). The one deliberate exception: `ConfigurationEvaluation::$anchorViewId` can be pre-set by a caller (`PlayConfigurator::goToView()`/`back()`) to request a specific anchor instead of the computed one — `ApplyFlow` honors it directly, skipping the Flow-rule scan and `lastAnsweredAtDepth` fallback entirely, but only after `GuardAnchorOverride` has verified it names an existing relevant `AnswerChunk` anchor (silently clearing it otherwise). If you find either "ResolveCurrentGroup" or "EvaluateGroup" mentioned elsewhere (older ADRs, comments), treat it as historical, not current.
- **"Answered" means "covered by a relevant `AnswerChunk`", not "has an `Answer` row".** Answers are append-only (`answers.answer_chunk_id`, no more unique `(configuration_id, view_id)`) — a view can have multiple historical `Answer` rows, only the one(s) whose chunk has `relevant = true` count as current. `ApplyFlow`'s `lastAnsweredAtDepth` and `BuildAnswerContext`'s `persistedAnswers` both filter to `Configuration::relevantAnswers()`/`relevantAnswerChunks()` — never the raw `answers()`/`answerChunks()` relations, which include superseded history. Revisiting an already-answered step (via the anchor-override above) makes `SupersedeAnswerChunks` mark that chunk and every later one (by `sequence`) `relevant = false` before a fresh chunk is committed; see `docs/adr/0007-back-navigation-via-answer-chunks.md` for the full reasoning, including why this is append-only rather than update-in-place or delete-on-revisit.
- **Groups never get a physical `Answer` row.** A Group view has no field value of its own, so "was this step completed" is derived, not stored: `BuildAnswerContext` synthesizes `persistedAnswers[$groupId] = true` whenever that view is the `anchor_view_id` of a relevant chunk. This is why `answers['{$step->id}'] == true` Flow-rule expressions (see `WidgetShowcaseSeeder`) work with zero rows ever written for the group itself — do not "fix" this by writing a real Answer for a Group id, and do not assume `Configuration::answers()` contains one row per visited step.
- `ComponentType::Breadcrumbs` (`ApplyBreadcrumbs`) lists the views that are anchors of a relevant chunk, in `sequence` order — i.e. the steps actually visited so far, not "views structurally shallower than the configured depth" (that was the pre-chunk implementation, and was wrong for branching flows: a sibling branch never taken is structurally shallower than nothing, but nothing in it was ever answered). This is also the eligible-target set for `PlayConfigurator::goToView()`.
- `RuleComponent` is `{Visibility, Validation, Flow}` — "next-group" was renamed to `Flow`. A Rule's `component` field says which stage owns it; `meta` is a JSON payload the owning component defines (a `Flow` rule's `meta.view_id` names the View to jump to when it fires).
- `ComponentType` is `{Visibility, Validation, Calculation, Scope, AnsweredViews, Breadcrumbs, PendingViews}` — one `Component` row per configurator per type holds pipeline-wide config (e.g. `Scope.config.depth`, `Calculation.config.formulas`). `AnsweredViews` is currently unused as a `componentContexts` key (nothing writes to it since `ApplyBreadcrumbs` moved to deriving breadcrumbs from relevant chunks directly) — it remains a recognized `ComponentType` for a future component that needs it, not dead code to remove on sight.
- Polarity is uniform: a Rule's expression evaluating `true` means its effect applies. Visibility: `true` → shown (default shown if no rule targets it). Validation: `true` → the answer is *valid*. Flow: `true` → jump to `meta.view_id` — `ApplyFlow` scans views from deepest/last backward, restricted to views at or above the target scope depth, and the first firing rule wins.
- For a purely linear multi-step wizard (no branching), give **every** step an explicit `Flow` rule (`answers[previous step id] == true`) rather than relying on `ApplyFlow`'s fallback (`lastAnsweredAtDepth`) to advance automatically — that fallback loops back to the first step whenever the last-answered view is nested deeper than the target scope depth, which is the normal case as soon as any leaf field inside a step has an answer.
- `Rule.expression` strings are evaluated with `symfony/expression-language`, and may contain `&&`/`||` themselves for compound logic. There is no separate Condition model or conjunction column (see `docs/adr/0006-view-unification-and-rule-condition-merge.md`).
- `ApplyCalculation` reads a `Calculation` component's `config.formulas` (name → expression), topologically orders them so a `calculation.<name>` reference resolves regardless of declaration order, and stores results on `$evaluation->context['calculation']`. Formulas, Flow rules, and Visibility rules all operate on raw PHP scalars from `answers`/`persistedAnswers` — no `ViewType`-specific coercion happens anywhere in the pipeline (see the `ViewType` rule for why).
- Auto-select is a recognized Rule component in the domain (see `CONTEXT.md`) but is intentionally unimplemented until a Configurator needs it. If you add it, it slots into the pipeline before validation.
