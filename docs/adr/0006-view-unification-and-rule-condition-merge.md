# Unify Group/GroupItem/Option into View; merge Condition into Rule

The original PartnerLink model split a Configurator's structure across three tables (Group, GroupItem, Option) and split its logic across two (Rule, holding a conjunction, and Condition, one expression clause per row, with a polymorphic `target`). Both splits were collapsed before any migration was written:

**View** replaces Group/GroupItem/Option as one self-referential tree: a `views` table with `parent_id`, `configurator_id`, a `type` discriminator (group/item-kind/option), an `order`, and a `config` JSON column for type-specific detail (a question's answer-type, validation limits). This trades the original's per-type columns/tables for uniformity: adding a new View type, or a new piece of type-specific config, doesn't require a new table or a schema migration touching multiple models — it's a new `type` value and a `config` key. The trade-off is weaker type-safety at the database level (a "group" View could technically be given "option" config); that's accepted because v1 has no editor UI to misuse it through, and this project's whole premise is being generic across configurators, not just one shape.

**Rule** absorbs Condition: one `rules` table with a nullable `view_id` (the View a rule concerns — nullable because a next-group Rule concerns the flow, not one View), a `component` (which pipeline stage owns it — visibility/validation/next-group), an `expression` string, and a `meta` JSON column the owning component defines the shape of (e.g. a next-group Rule's `meta` names the View to jump to). The original's per-clause Condition rows plus a `conjunction` column are dropped entirely — `symfony/expression-language` already supports `&&`/`||` inside one expression string, so splitting a compound condition across multiple rows was solved machinery the original needed (likely for a visual rule-builder UI) that this project doesn't have in v1, per ADR 0004's no-editor-UI cut. If an editor UI is built later and needs to construct compound expressions from discrete clauses, that's a UI-layer concern — it can compose one expression string rather than requiring the storage layer to split them.

This also incidentally removes the original's polymorphic `target`/`parent` relations everywhere (Condition→target, Content→parent): now that Group/GroupItem/Option are one model, every such relation becomes a plain foreign key to `views.id`.
