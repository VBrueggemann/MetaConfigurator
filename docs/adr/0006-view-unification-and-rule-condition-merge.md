# Unify Group/GroupItem/Option/Content into View; merge Condition into Rule

> **Superseded detail:** the concrete `type` list below (`group`/`select`/`text_input`/`html`) and "next-group" `component` naming are stale — see `CONTEXT.md` for current View/Rule vocabulary and `.ai/rules/livewire.md`'s `ViewType` rule (`{Group, Input, Display}`, config-driven `config['widget']` instead of enumerated types). The reasoning here — one self-referential `View` tree instead of Group/GroupItem/Option/Content, and `Rule` absorbing `Condition` — still holds.

The original PartnerLink model split a Configurator's structure across three tables (Group, GroupItem, Option), kept display content in a fourth (Content, polymorphically attached), and split its logic across two more (Rule, holding a conjunction, and Condition, one expression clause per row, with a polymorphic `target`). All of this was collapsed before any migration was written:

**View** replaces Group/GroupItem/Option/Content as one self-referential tree: a `views` table with `parent_id`, `configurator_id`, a `type` discriminator (`group` | `select` | `text_input` | `html`), an `order`, and a `config` JSON column for everything else that varies by type. A `select` View's config carries its options directly as value/label pairs plus whether multiple are allowed — there is no separate Option model/View. An `html` View's config carries the static content it renders — there is no separate Content model; it's just another View type. This trades the original's per-type columns/tables (and its separate Option and Content models) for uniformity: adding a new View type, or a new piece of type-specific config, doesn't require a new table or a schema migration touching multiple models — it's a new `type` value and a `config` key. The trade-off is weaker type-safety at the database level (a `group` View could technically be given `select` config); that's accepted because v1 has no editor UI to misuse it through, and this project's whole premise is being generic across configurators, not just one shape.

**Rule** absorbs Condition: one `rules` table with a nullable `view_id` (the View a rule concerns — nullable because a next-group Rule concerns the flow, not one View), a `component` (which pipeline stage owns it — visibility/validation/next-group), an `expression` string, and a `meta` JSON column the owning component defines the shape of (e.g. a next-group Rule's `meta` names the View to jump to). The original's per-clause Condition rows plus a `conjunction` column are dropped entirely — `symfony/expression-language` already supports `&&`/`||` inside one expression string, so splitting a compound condition across multiple rows was solved machinery the original needed (likely for a visual rule-builder UI) that this project doesn't have in v1, per ADR 0004's no-editor-UI cut. If an editor UI is built later and needs to construct compound expressions from discrete clauses, that's a UI-layer concern — it can compose one expression string rather than requiring the storage layer to split them.

This also incidentally removes the original's polymorphic `target`/`parent` relations everywhere (Condition→target, Content→parent): now that Group/GroupItem/Option/Content are one model, every such relation becomes a plain foreign key to `views.id`.
