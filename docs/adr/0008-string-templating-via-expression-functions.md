# String templating via `{{ }}` substitution and expression functions

> **Superseded detail:** `message(id)` was later renamed `validationError(id)`, and the classes named below (`BuildTemplateFieldContext`, `ResolveTemplateField`, `BuildAnswerContext`) were renamed/restructured into `CollectAndBatchFetchExternalReferences`/`ResolveModelFunction`/pipeline `context` as the mechanism grew to cover more than templating (see `.ai/rules/pipeline.md`). The four templatable fields also moved from raw `config`/`meta` strings into a separate polymorphic `Template` model (see `.ai/rules/models.md`) rather than being resolved in place. The reasoning here — substitution-only templates, UUID addressing, a configurable function/field registry, raw-text fallback on an unresolved reference — still holds.

Content authors write `View.config['label']`/`config['content']`/`config['options'][].label` and `Rule.meta['message']` as static strings. There was no way for a later step to echo an earlier answer, or for a Display step to surface an already-computed `Calculation` result — every such need had to be hand-copied by whoever authored the seeder, with no way to keep it in sync as answers changed.

Three questions had to be settled before this could be built: how a template addresses an answer or another item, how much expressive power a template gets, and what happens when a reference can't be resolved.

- **A new human-readable `key` column on `views`** (so a template could read `{{ answers.shoe_size }}` instead of a raw UUID) was rejected in favor of keeping the existing UUID addressing, via the same bracket-string convention `Rule.expression` already uses (`answers['<uuid>']`). Configurators are authored via seeders/fixtures only in v1 (see `docs/adr/0004-v1-scope-cuts.md`), so there is no authoring UI a friendlier key would actually serve yet, and it would be one more thing to keep unique and in sync with no consumer.
- **Inline arithmetic/conditionals inside templates** (e.g. `{{ answers.a * answers.b }}` evaluated directly wherever it appears) was rejected in favor of substitution-only. Real computation stays exactly where it already lived — a named `Calculation` formula, with its existing topological sort and circular-dependency detection (`ApplyCalculation`) — and a template can only display an already-computed `calculation.<name>` or raw `answers[id]`. This keeps "logic" in one place instead of duplicating an evaluator inside every label.
- **Exposing item metadata (a View's label, a Rule's message) as more context-array namespaces** (`views[id].label`) was rejected as the public surface in favor of two new ExpressionLanguage functions, `label(id)` and `message(id)`, registered in `ExpressionLanguageServiceProvider` alongside the existing `strlen`/`count`. Both are backed by a small configurable registry (`config/templating.php`: model class → field name → accessor), read by `BuildTemplateFieldContext` into `context['templateFields']` and resolved through `ResolveTemplateField`. Adding a new item type or field later is a registry edit, not new resolver code — this is the "configurable" requirement that drove the whole design.
- **Hardcoding which `View.config` keys get self-resolved** inside `ResolveTemplateStrings` (an `if (isset($config['label'])) ...` per field) was rejected the same way, for the same reason: `config/templating.php` also carries a `resolvable` entry per model class, one closure per config key, each given that key's current raw value, the `ResolveTemplate` action, and the context, returning the new value for that key. `ResolveTemplateStrings` itself only knows to extract `$config[$key]`, call the closure, and write back whatever it returns — it has no field-name-specific logic left, and the closures themselves know nothing about `View` at all. `label`/`content` are one-line closures over a plain string (`$resolveTemplate($template, $context, ...)`); `options` is the one closure that takes the raw array instead and still has to loop internally, since it's resolving each option's `label` inside a list rather than a single scalar.

**Chosen**: `{{ expression }}` spans inside `config['label']`/`config['content']`/`config['options'][].label`/`Rule.meta['message']` are found and evaluated by `ResolveTemplate` via the existing `EvaluateExpression`/`symfony/expression-language` machinery — no new parser. Any failure to resolve a match — an unknown reference, an answer not yet given, or a circular `label()`/`message()` reference — is caught and that one match is left as its original raw `{{ ... }}` text, the same way Laravel prints back a missing translation key rather than erroring. Circular references are guarded by threading a `__resolving` set of `"{namespace}.{id}.{field}"` keys through the context on each recursive `ResolveTemplateField` call — stateless, since the shared `ExpressionLanguage` instance is a singleton and can't hold per-call mutable state itself.

`content` renders raw (`{!! !!}`, trusted author HTML) and so is the one field where `ResolveTemplate` is asked to escape (`escapeValues: true`) — only the substituted *value* per match, never the author's literal surrounding markup, so a `<script>`-bearing answer can't come back as a stored-XSS payload. Every other field (`label`, `options[].label`, `message`) renders through Blade's own escaped `{{ }}` and must not be pre-escaped, or the substituted portion would be escaped twice.

`BuildTemplateFieldContext` sits early in `FetchConfigurationState::PREFIX` (right after `GuardAnchorOverride`, shared with `CommitConfigurationAnswers`) so `label()`/`message()` — and `Rule.meta['message']` templating inside `ApplyValidation`, which needed no visible-string rendering change, only a resolve call before the message is stored — work identically at fetch and commit time. `ResolveTemplateStrings` itself, which rewrites the `View` tree in `componentContexts['scope']` before it reaches Blade, only runs in the fetch pipeline: `PlayConfigurator::next()` already discards the commit pipeline's evaluation on success and re-fetches for rendering, so resolving strings there too would be wasted work. Because both new pipeline stages mutate already-loaded, in-memory models and never call `->save()`, nothing about this feature persists a resolved string back to the database — the same seeded template renders fresh against whatever `context` a given request produces, including this same step's not-yet-committed answers (`BuildAnswerContext` already merges `pendingAnswers` into `context['answers']`, so this needed no new plumbing at all).
