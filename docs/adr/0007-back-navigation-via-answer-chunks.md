# Back-navigation and answer revision via append-only AnswerChunk history

Scope was, until now, purely forward-computed from `Answer` rows with no way to revisit an already-answered step. Adding "go back and overwrite an answer" required deciding what happens to whatever came after the step being revised.

Three approaches were considered and rejected before settling on the current design:

- **Update-in-place with no invalidation** (keep the old unique `(configuration_id, view_id)` Answer, just overwrite the value): cheapest, but leaves no way to tell "answered as part of the current path" apart from "answered once, possibly under since-changed circumstances" — every consumer of "is this view answered" (`ApplyFlow`'s `lastAnsweredAtDepth`, Flow-rule `answers[...]` expressions) would need to reason about staleness itself.
- **Rule-dependency-based selective invalidation** (walk Flow/Visibility expressions to figure out exactly which later answers were actually affected by the change, clear only those): correctness-wise the most precise, but determining "affected" is a real static-analysis problem — a Flow rule not changing its target doesn't mean nothing meaningful downstream changed, and the pipeline's expressions are opaque `symfony/expression-language` strings, not a dependency graph.
- **Delete-on-revisit** (drop every Answer from the revised step onward, forcing the user to redo them from scratch): simple and matches "everything after this point is now unknown," but throws away information that's still useful — if the user's edit doesn't change which branch they end up back on, re-typing already-given answers is pure friction.

**Chosen**: a new `answer_chunks` table, one row per step commit (`configuration_id`, `anchor_view_id`, `relevant` boolean, `sequence`), with `answers.answer_chunk_id` replacing the old per-view unique constraint — answers are now append-only history, never updated in place. This mirrors the original PartnerLink model's `AnsweredGroup` (one row per answered-group episode, its own `relevant`/`order`), adapted to this project's View/Rule vocabulary as `AnswerChunk`/`sequence`. Revisiting an already-answered step marks that chunk and every later one (by `sequence`) `relevant = false`, then appends a fresh chunk — nothing is ever deleted. `ApplyFlow`/`BuildAnswerContext` treat only `relevant = true` chunks (and their answers) as truth, so superseded answers can never leak into computed scope, visibility, or validation; `PlayConfigurator::loadValues()` is the one place that *does* look past `relevant = false` rows, using the most recent stale answer as a nicer prefill than the static `config['default']` when a field is reached again with nothing currently answered.

Two new pipeline stages carry this: `GuardAnchorOverride` (fetch pipeline, first stage) validates a caller-requested anchor view against the configuration's relevant chunk anchors, silently clearing it if illegitimate rather than throwing — an invalid request just falls back to whatever `ApplyFlow` would have computed anyway, since a stale breadcrumb click is not an error condition worth surfacing. `SupersedeAnswerChunks` (commit pipeline, before `CommitAnswers`) does the actual invalidation, only when the commit's resolved anchor is already an existing relevant chunk (i.e. a genuine revisit, not a fresh next step). They're separate stages because they answer different questions — "is this target legitimate" versus "what does committing to it invalidate" — matching how PartnerLink's `PathingService::handleAnswering` does both, but as one step; splitting them here keeps each stage single-purpose per this project's existing one-concern-per-pipeline-stage convention.

Groups still never get a physical `Answer` row for "was this step completed" — that would have meant writing a throwaway boolean row into `answers` on every single commit, multiplying indefinitely under an append-only model every time a step gets revisited. Instead `BuildAnswerContext` synthesizes `persistedAnswers[$groupId] = true` for any Group that is a relevant chunk's `anchor_view_id`, so the existing `answers['{$step->id}'] == true` Flow-rule convention (see `WidgetShowcaseSeeder`) keeps working unmodified, with nothing fake ever persisted.
