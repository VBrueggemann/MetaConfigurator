# Rules engine as an ordered, dependent Pipeline — not independent events

The rules engine needs to run three concerns per evaluation — Visibility, Validation, NextGroup — and produce one combined result a Livewire component renders from. Two shapes were considered: Laravel events/listeners, where each concern reacts independently and none reads another's conclusions; or `Illuminate\Pipeline\Pipeline`, where concerns run in a fixed order and later stages may read earlier stages' output.

Events were tried first, on the reasoning that independence keeps concerns decoupled. That was reversed in favor of Pipeline, because the concerns are not actually independent: Validation must only check GroupItems that Visibility has determined are shown, and NextGroup must only branch on Answers that passed Validation. Modeling that as strictly independent listeners would just push the ordering dependency into ad-hoc coordination logic elsewhere. The Pipeline runs stages in the order **Visibility → Validation → NextGroup**, threading one shared evaluation-result object that each stage reads and adds to. AutoSelectRule, if it's ever built, would slot in before Validation (auto-selected values should be validated like any other answer).
