# Rules engine as an ordered, dependent Pipeline — not independent events

The rules engine needs to run three components per evaluation — visibility, validation, next-group — and produce one combined result a Livewire component renders from. Two shapes were considered: Laravel events/listeners, where each component reacts independently and none reads another's conclusions; or `Illuminate\Pipeline\Pipeline`, where components run in a fixed order and later stages may read earlier stages' output.

Events were tried first, on the reasoning that independence keeps components decoupled. That was reversed in favor of Pipeline, because the components are not actually independent: validation must only check Views that visibility has determined are shown, and next-group must only branch on Answers that passed validation. Modeling that as strictly independent listeners would just push the ordering dependency into ad-hoc coordination logic elsewhere. The Pipeline runs stages in the order **visibility → validation → next-group**, threading one shared evaluation-result object that each stage reads and adds to. Each Rule names which component it belongs to (its `component` field); auto-select, if it's ever built, would slot in before validation (auto-selected values should be validated like any other answer).
